# Large received files

The November 2026 audit found that the transport already uses bounded sender reads, SHA-256 validation, native channel backpressure and receiver commit credits. Wire chunk indices are unsigned 32-bit integers; byte offsets use safe JavaScript numbers. Both 50,000,000,000 bytes and 50 GiB fit those limits with the current chunk sizes. These facts alone do not certify a complete 50 GB transfer on two physical devices.

New received files larger than 32 MiB use `storageFormat: 'extent-v1'` in their metadata. Each actual receive batch is packed into contiguous records of at most 1 MiB. Partial timer batches and final tails are committed immediately; packing never waits to fill a record. Chunk bytes and progress metadata commit in the same IndexedDB transaction, and the sender receives credit only after that transaction completes. The existing database remains version 4 with the same stores and compound key. Files without the marker retain their legacy one-record-per-wire-chunk interpretation. Saved rooms and their existing files keep working without a migration or rewrite.

Range reads locate a predecessor key and scan only the relevant records, returning at most 1 MiB. Readers check sizes, chunk counts, gaps, overlaps, file identity and EOF. `getChunkIndices` still returns logical wire indices for small diagnostics; it must not be used to inspect an entire 50 GB file. Deletion uses one compound-key range request with metadata deletion in the same transaction. Receiver storage preflight reserves the payload plus 32 MiB and 1% for large files; the browser's estimate is advisory, and a failed commit reports a storage error and removes the incomplete receive.

Completed large local previews stream directly from IndexedDB through `/__peerlink_local_preview/`. They work without a peer or room connection and support GET, HEAD and byte ranges, with no extra full-file OPFS copy. New previews never stage bytes in OPFS. A bounded best-effort cleanup still removes old `.peerlink-preview-TIMESTAMP-*` crash leftovers after 24 hours, using the old exclusive `ifAvailable` lock to protect previews still open in an older tab. Unsupported preview streaming provides an actionable Download fallback. Text previews show and label only the first 256 KiB, served as plain text. Image/PDF previews above 32 MiB are rejected with a Download suggestion, including queued and remote files; oversized images skip thumbnail decoding. Preview responses use sandbox CSP and `nosniff`. These application buffer bounds do not bound a browser media decoder's memory for arbitrary files.

The controlling service worker must return an actual version 2 capability ACK for packed-file downloads and new local/remote previews. This also covers an old active worker with no waiting registration. An old worker can still download legacy rows after a version 1 ACK; applying the PeerLink update is required for new features. New downloads retain the 30-second startup timeout. Version 2 workers send byte progress at most once every five seconds; only increasing bytes refresh the two-minute idle watchdog. Healthy transfers have no fixed total duration limit. Legacy version 1 workers cannot report bytes, so their supported legacy downloads have no activity watchdog.

## Checks

Run `node --test tests/large-transfer.test.mjs tests/preview-http.test.mjs` for packing, virtual high-offset sender reads and SHA-256, local preview HTTP and abort handling, remote text prefixing, capability/version compatibility, download watchdog behavior beyond 30 simulated minutes, slow-storage ACK ordering, partial timer commits, cancellation and failed-commit cleanup. These VM checks allocate only bounded source ranges, including offsets above 4 GiB and around 50 GB/50 GiB.

Open `/tests/large-transfer-bounded.html` and click **Run bounded checks**. This writes a 33 MiB + 123 byte OPFS source in at most 1 MiB writes, sends it through the real worker and transfer engines over ordered in-page channels, verifies every received byte, checks packing and local preview ranges, and exercises actual IndexedDB sparse high offsets, legacy rows and corrupt range rejection. It deletes the source and sparse records, retaining the small received copy for **Verify attachment stream**, **Download received test file**, and **Delete received test file**. The attachment stream control verifies response headers, every byte, bounded output, owner notifications and one-use tokens without relying on native download UI. The fixture never runs automatically. Compile it with `node node_modules/typescript/bin/tsc --noEmit --target ES2022 --module ESNext --moduleResolution bundler --lib "ES2022,DOM,DOM.Iterable" --types vite/client --skipLibCheck tests/large-transfer-bounded.ts`.

The current CUA browser check verified 34,603,131 exact received bytes in 67 packed records instead of 2,129 wire records, sparse 4 GiB/50 GB/50 GiB boundaries, and local preview HEAD/range/416/cancel behavior. Full physical-device 50 GB transfers, multi-hour native downloads, browser restarts and browser codec behavior remain outside this bounded check. Browser site quota and real free disk space must cover the received copy plus working space; saving a separate download needs destination space too. Connection/browser interruptions restart the transfer; this change does not add cross-session resumption. Do not run the older 2 GiB fixture by default on a low-space profile.
